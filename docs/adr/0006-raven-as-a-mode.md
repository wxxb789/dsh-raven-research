# Isolate Raven to a selectable mode that inherits the deployment's own base preset live

ADR 0005 put Raven's whole row on the Host plane. Because `tools` and `system-prompt` are layered registries, a host row lands in the global layer and every agent sees `raven_task` without opting in. That was recorded there as the intended meaning of installing Raven. It is the wrong default: a coding session, a compaction agent, and a one-shot subagent all pay for a research tool and its system-prompt section, and none of them asked for it. This ADR supersedes 0005's host-plane placement, and it now supersedes more of 0005 than that. **The Profile Bundle contract is gone**: this package no longer declares `dsh.bundle`, so `dsh plugin add` mounts nothing by default and `cordis.patch.yml` is demoted to an opt-in overlay a deployment applies deliberately. **The browser settings card is no longer a default surface** but an opt-in that costs isolation, for the reason recorded at the end of this ADR. What does survive from 0005 is the card's implementation and the two costs accepted for reimplementing it — the card still exists and still works; it simply is not mounted unless asked for.

`RavenConfig` gains `role?: 'host' | 'agent' | 'both'`, defaulting to `'both'` so an existing out-of-tree row that names no role keeps working. `host` registers only the settings namespace and the mount-time capability warning. `agent` registers only `raven_task`, the system-prompt section, the agent pre-step Task context, and the `tools/ptc-dispatch-log` waterfall. Raven then ships as two halves: the bundle's host row, and a `raven` agent preset that makes Raven a MODE in the new-session UI.

A mode is not a new mechanism. It is an agent preset directory — `preset.yml` plus `agent.cordis.yml` — discovered by `@deepseek-ai/dsh-agent-presets`, which scans its configured roots and then `$DSH_HOME/.agent-presets` under its own `includeUserRoot`. That is why `legion` and `code-compact-60` are modes. Installation writes that directory, performed by the shipped `dsh-raven-install-preset` bin, and is NOT a bundle patch of the `agent-presets` row: a patch can only replace a row's whole config by id, so it would have to restate that row's `default` and `roots` as a second copy that silently overrides the base — the exact failure this repository just spent a day removing from its own Harness pin.

The preset INHERITS a base composition rather than shipping one, and that is the second decision here. A preset's `agent.cordis.yml` is the whole agent composition — persona, tool rows, shell, compaction — not an overlay on a default; even the shipped `minimal` preset mounts a persona plus PTY and filesystem groups. A preset holding only Raven's row would boot an agent with no persona, no tools and no shell. The alternative, shipping a copy of a Harness composition inside this npm package, would place someone else's 13 KB file where this package cannot see it change, so it would drift silently and forever. What ships instead is Raven's row as a FRAGMENT, and the installer resolves a base preset from the roots the Harness itself scans, then writes a composition that INCLUDES it and inserts the row — the live default decided below; inlining that base's own text is now only the `--snapshot` fallback. It fails loudly naming every location it tried when it can find no base, rather than inventing a composition. A bare package name is legal in that row because `PresetTree.import()` resolves bare specifiers from the host composition's base rather than the preset's own directory, precisely so a locally authored preset can name packages it does not sit beside.

**The base is now INCLUDED LIVE, and this reverses what this ADR previously decided.** An earlier revision recorded the opposite: that the base should be INLINED as text and that a nested `cordis:include` should be avoided entirely. That decision bought safety by giving up the property the mode was asked to have. A snapshot cannot inherit "the latest version of PTC mode" — it inherits whatever `ptc` preset existed on the day someone last ran the installer with `--force`, and every Harness upgrade silently widens the gap. The requirement is live inheritance, so the include is the mechanism and the hazard is closed rather than avoided.

`cordis:include` reads its file at MOUNT time, so an include of the package-discovered `ptc/agent.cordis.yml` is exactly live inheritance — a Harness upgrade that changes that file changes the Raven mode on the next mount. The installed composition therefore shrinks from a ~16 KB copy to a ~2 KB file, and its shape is TWO TOP-LEVEL SIBLING ROWS: one `cordis:include` row naming the resolved base, and beside it, at the same level of the same document, one row carrying `id: raven-research` / `name: dsh-raven-research` / `config: { role: agent }` — under a header stating that nothing here is a snapshot. Raven's row is a SIBLING of the include and never a member of the include's `patches` list; the reason is the hazard recorded next.

**The destructive-write hazard is REAL, it reproduces, and it is what dictates the sibling shape.** `Include` rebases its child tree onto the directory of the file it included. A row inserted through the include's `patches` list is therefore resolved from inside the HARNESS INSTALL, where `dsh-raven-research` is not installed; the include fails to apply; and the failing tree is written back as `[]`. Nothing suppresses that write: a nested include under a preset is instantiated from the plain `Include`, not the `PresetTree` subclass whose `write()` is a deliberate no-op precisely because the inherited write "in practice means truncating a shipped composition to `[]` the first time a session ends".

This happened. A deployment's shipped `code` preset was found truncated from 13605 bytes to 3. A side-by-side run over a copy of that same base reproduced it exactly: the patched shape failed to mount and left a 3-byte base, while the sibling shape mounted and left the base at 13605 bytes. Mounting the shipped sibling shape through the real `agentPresets.standingKeyFor` gives host-only tools `[]`, roster `["raven"]`, an installed file of 1981 bytes, and the base still 13605 bytes afterwards.

An earlier experiment had appeared to CLEAR the patched shape, and it was INVALID: the base it used was itself `[]`, so a truncating write produced a file byte-identical to the one it started with. A negative result about destruction needs a base whose content a write would visibly replace; that one had none, and it hid a live hazard behind an unchanged file. The conclusion that follows is about SHAPE rather than permissions: the guard is emitting a composition that RESOLVES, not asking for a permission bit on a file this package does not own.

**And the installer must never touch the Harness at all.** Raven is a plugin OF a deployment, not a co-owner of it. Setting a permission bit on the deployment's own preset file would be a modification of someone else's install, so this installer sets none and no flag offers to — which is also why the guard had to be a shape that resolves rather than a permission bit. Every write this installer makes lands inside `$DSH_HOME/.agent-presets/raven`. No file outside that directory is written, moved, renamed, or has an attribute changed.

Prevention of the shape hazard is one thing; a base that something ELSE wrote is another, so the installer also DETECTS, which costs nothing and touches nothing. The generated header records the base file's `sha256` at install time and every later run compares it, distinguishing two conditions that call for opposite reactions. A base that merely moved on is an ordinary Harness upgrade: it is reported as expected, with the explicit statement that nothing needs doing because live inheritance already picked it up, and the run still exits zero as up to date. A base whose content now contains Raven's own row means something wrote a patched composition back into the Harness install: that is a warning naming the file and telling the operator to restore it from their Harness installation, because this installer cannot have caused it. The recorded digest is deliberately excluded from installed identity — it is detection state, not a re-sync trigger — so an upgraded base never demands `--force`; the stale digest is refreshed in place instead.

One concrete API fact shapes the generated file. The include resolves its `path` with `new URL(path, ctx.baseUrl)` and then `fileURLToPath`, and a bare Windows absolute path is not relative-resolved at all: in `Q:\...` the `Q:` parses as a URL SCHEME, so the result is `q:\...` and `fileURLToPath` rejects it with `ERR_INVALID_URL_SCHEME` — reproduced directly. The installer therefore writes the base as a `file://` URL via `pathToFileURL(basePath).href`, which is absolute and legal input to both halves of that pair on every platform, and a test covers Windows-shaped paths including one containing spaces.

The fragment stays a FILE — `presets/raven/agent.cordis.yml` — rather than a string constant inside the installer, and the tarball is where that choice is load-bearing. A file keeps the row reviewable as YAML, keeps its comments beside the rows they explain, and lets the bundle test parse it as a composition rather than assert against an escaped string. The cost is that it must be named in three allowlists that no single reader sees together: `files` in `package.json`, `expectedFiles` in `scripts/verify-packed-install.ts`, and the bundle test. That cost was paid once already: with the row file briefly absent from the working tree, `files` still named it, and a `files` entry matching nothing contributes nothing and says nothing — so `pnpm pack` produced a tarball carrying the installer and no row for it to append. The bundle test now reads both preset files off disk through the same paths the manifest publishes, so a missing row fails the ordinary test run instead of surviving to a tarball.

The SNAPSHOT path is kept as a fallback under `--snapshot`, with its generated digest header and its `--force` re-sync intact, for a deployment that would rather not depend on a file outside this package at all — an install whose preset directory may move, a machine where the base is fetched per-boot, an operator who wants the mode to keep working with the Harness uninstalled. It composes the base's text verbatim followed by Raven's row. Text, deliberately: a YAML round-trip would discard the base's comments, which are most of what a composition teaches its next reader. It pays exactly the staleness the default now avoids, and the installer says which relationship each install has in a line of its own output.

The rejected alternatives keep their reasons. Shipping a copy of a Harness composition inside this npm package is still rejected: it would place someone else's 13 KB file where this package cannot see it change, drifting silently and forever, and it is now doubly pointless because the include does not need a copy at all. Patching the `agent-presets` row from the bundle is still rejected: a bundle can only replace a row's whole config by id, so it would restate that row's `default` and `roots` as a second copy silently overriding the base — the exact failure this repository spent a day removing from its own Harness pin. And a preset carrying only Raven's row is still rejected, because a preset's `agent.cordis.yml` is the whole agent.

What live inheritance costs, plainly. The mode now depends on a file OUTSIDE this package: the installed composition names the package-discovered base preset as a `file://` URL, so moving or deleting that preset breaks the mode where before it merely made a copy stale, and the failure surfaces at mount rather than at install. A deployment that would rather not carry that dependency gets `--snapshot` and its staleness back. Two install modes is itself a cost: the installer now has two shapes of generated file and two idempotence stories. And detection is weaker than prevention by construction — it reports damage after the fact instead of making it impossible — which is the honest consequence of an experiment that bounded the hazard rather than eliminating it, and of the harder constraint that a plugin may not modify the deployment it plugs into.

The split is safe because event admission extends UP the scope chain and `tools/ptc-dispatch-log` is scoped to `dispatch.agent`. An agent-scoped listener therefore still receives its own agent's PTC mode sub-dispatches, so the durability seam that records a Task step taken from inside `run_code` does not need the host plane. 0005 named that waterfall as a second reason for host placement; that reason does not hold. The settings namespace was the only surviving reason, and the isolation decision below rejects it as a default too: nothing is mounted on the host plane unless a deployment opts in. A preset row publishing into the root service realm would be rejected by `agent-presets`, but Raven publishes no Service, so an agent-plane row is legal without an isolate realm.

What is gained: Raven applies only in Raven mode. Choosing the mode is the act of asking for it, which is what a user picking "Raven" in the new-session UI already means, and every other mode's tool catalog and system prompt are unchanged.

What is paid, plainly. Other modes lose `raven_task` — a coding session can no longer be asked mid-flight to open a research Task, and the answer is to start a session in Raven mode. The preset itself mounts once under a standing scope and every Raven session joins it; Raven therefore keys mutable books by Agent identity or successfully detected Team identity inside that shared instance. This preserves per-Agent/per-detected-Team isolation. Team ownership is conditional on the experimental membership probe, and after a process restart member histories fold into the Team book as those members are observed. Replay restores the latest successfully persisted snapshots; an oversized nested PTC mode log may omit that one step without making the session unloadable.

**Nothing stays on the host plane by default, and that reverses the last paragraph this ADR used to end with.** That paragraph kept the `raven-research` settings namespace on the host plane because only a process-wide mount keeps its card visible between sessions. It was right about the mechanism and wrong about the goal. The requirement is that Raven is ISOLATED to its mode: if a user wants Raven they switch to Raven mode first, and from any other mode they see nothing of it. A host-plane settings namespace defeats exactly that, because a settings page is a GLOBAL surface — a user sitting in PTC mode who opens Settings still finds a Raven card, and by the requirement's own definition that is Raven being visible in another mode.

So the host row stops being part of the install. The package contributes NOTHING until a session is started in Raven mode: no `raven_task`, no system-prompt section, no pre-step Task context, and no settings card. Choosing the mode is the only way to obtain any of it.

Isolation and the card cannot both be had, and this is the honest statement of why. Served from the host plane the card is visible from every mode; served from inside the preset it would appear and vanish with a session using that preset, which is a worse card rather than an isolated one. There is no third mount that is both persistent and mode-scoped, because persistence across sessions is precisely what "not scoped to a session" means. Isolation was chosen.

Raven's configuration therefore moves into the PRESET ROW. The row the installer inserts carries its own `config:` block — the same fields the settings card edited — so a deployment configures Raven where the mode is defined, in a file scoped to exactly the mode that mounts it. The shipped fragment lists every field; compatibility-sensitive network policy and timeout fields are explicit at safer new-install values, while omitted legacy configurations retain their schema compatibility defaults and the remaining fields stay commented.

The settings card survives as an EXPLICIT OPT-IN that breaks isolation, and is documented as that rather than as a step. A deployment that would rather have the card than the isolation mounts the host row from `cordis.patch.yml` itself and accepts that Raven becomes visible from every mode's Settings. When it is mounted the preset row's values become the base layer, with `settings.yaml` overriding them while the provider is composed and the preset values authoritative again if it goes away — the layering is unchanged, only its default presence is.

What this costs, plainly. Raven's settings are edited in a YAML file rather than in the UI, which is worse for a person who wanted a card and does not want to find a preset directory; changing a value means editing the mode and starting a new session rather than clicking. The mount-time capability warning that rode the host row is gone by default too, so a deployment missing an optional capability learns it from the mode's own behaviour rather than from a global card. And the package now has a configuration surface that is documented in three places — the shipped fragment, the installed file, and the READMEs — which is a maintenance cost that a single settings schema did not have.
