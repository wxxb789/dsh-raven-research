# Use llm-wiki as Raven's durable Workspace format

A Raven Task is a bounded unit of research or writing whose state is replayed from the owning Harness session. A Raven Workspace is a separate, user-owned, long-lived knowledge repository. Completing or stopping one does not close the other, and a user may run Raven Tasks without ever creating a Workspace.

Raven uses the existing llm-wiki layout (`wiki/SCHEMA.md`, `wiki/index.md`, `wiki/log.md`, immutable `raw/` sources, and maintained `queries/entities/concepts/comparisons` pages) rather than inventing a Raven repository format. The models are isomorphic: immutable raw pages are inspected Source material, `sources:` is page-level provenance, `confidence` is an evidence ceiling, `contested:` and `contradictions:` retain disagreement, and `sha256` detects stored-body drift. Extra Raven provenance such as `raven_tasks`, `inspection_call_id`, and `supersedes` is additive frontmatter that ordinary llm-wiki and Obsidian readers may ignore.

Markdown files are authoritative. `wiki/index.md` is a deterministic, disposable projection over those pages and can always be regenerated. Raven adds no required manifest, database, embedding model, or vector store. A future optional lexical or vector index may be another disposable projection, but no core Workspace operation may depend on it.

Raven registers a separate `raven_workspace` tool for Workspace lifecycle. It accepts exact Markdown snapshots already inspected by ordinary Harness file tools and returns a conditional file plan; it never reads or writes the filesystem itself. Every write states an `absent` or current-content `sha256` precondition. Global `health` and `maintain` operations additionally require an explicit `complete=true` attestation, so a partial snapshot cannot report healthy or replace the global index. Log appends carry deterministic operation markers and are appended only when that marker is absent. The Harness agent re-reads targets, enforces the preconditions, applies the bytes with ordinary file tools, and re-reads the result. This keeps filesystem access, approvals, and sandboxing in the Harness boundary.

Adoption and migration are expand-only by default. Adopting an existing llm-wiki preserves every existing page byte and creates only missing standard structure. Adopting a regular folder leaves every Original Resource in place and writes immutable normalized-Markdown pages under `wiki/raw/documents/`. Existing Markdown remains original; other non-web media must arrive through the Source layer's established Markdown normalization contract with Original Resource URI, media type, producer, coverage, inspection call, and exact Markdown bytes. Web material enters through a completed Task contribution because the Task verifier attests excerpts, not arbitrary caller-supplied full-page Markdown. Failed or unavailable normalization is reported rather than silently skipped. Repeating the same material is a no-op; changed material creates a new content-addressed raw revision linked to its predecessor with `supersedes`.

A completed Task may grow a query, concept, entity, or comparison page without mutating the Task. The page retains prior body history, source links, contributing Task IDs, conservative confidence, and contradiction identities. Repeating the same Task contribution is a no-op. The compatible one-off `raven_task action=export` projection remains available for users who do not want a maintained Workspace.

Workspace reuse is lexical and transparent. `raven_workspace action=reuse` ranks supplied Markdown pages by titles, tags, and body terms and labels every result as stored knowledge. For current or volatile questions it also requires fresh verification; the agent must reopen the authoritative Original Resource rather than treating an old Workspace page as current evidence. This compounds durable knowledge while preserving the distinction between remembered understanding and newly verified facts.
